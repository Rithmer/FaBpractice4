# ТехМаркет — Интернет-магазин техники

Full-stack приложение интернет-магазина с микросервисной архитектурой, балансировкой нагрузки, кэшированием, брокером сообщений, GraphQL API и интеграцией Stripe.

## Что реализовано по практикам

### Практика 19 — PostgreSQL (реляционная БД)

**Для чего:** хранение пользователей и токенов с чёткой структурой и связями.

* Используется PostgreSQL.
* Таблицы:
  * `users`
  * `refresh_tokens`
* Реализована работа через SQL.
* Все маршруты пользователей связаны с БД.

---

### Практика 20 — MongoDB (NoSQL)

**Для чего:** гибкое хранение товаров без жёсткой схемы.

* Используется MongoDB.
* Коллекция:
  * `products`
* CRUD операции реализованы через ODM.
* Данные товаров полностью перенесены из SQL.

---

### Практика 21 — Redis (кэширование)

**Для чего:** ускорение ответов и снижение нагрузки на БД.

* Подключён Redis.
* Реализовано кэширование:
  * `GET /api/products`
* TTL кэша: ~60 секунд.
* Добавлена инвалидация кэша при изменении данных.
* Заголовок ответа:
  * `X-Cache: HIT / MISS`

---

### Практика 22 — Балансировка нагрузки (Nginx)

**Для чего:** распределение запросов и отказоустойчивость.

* Используется Nginx как reverse proxy.
* Запущено **2 backend-сервера**:
  * `backend1`
  * `backend2`
* Алгоритм: Round Robin.
* Проверка через `/health`.

---

### Практика 23 — Docker Compose (контейнеризация)

**Для чего:** удобный запуск всей системы одной командой.

* Все сервисы упакованы в Docker:
  * `backend1`, `backend2`
  * `frontend`
  * `nginx`
  * `mongo`
  * `redis`
* Запуск одной командой:

  ```bash
  docker compose up --build
  ```

---

### Практика 24 — WebSocket и Socket.io (реалтайм)

**Для чего:** мгновенные уведомления без перезагрузки страницы.

* Подключён Socket.io.
* Реализованы события в реальном времени:
  * Уведомление о появлении отслеживаемого товара.
* Клиент подписывается на события сразу после входа.
* Сервер эмитит события при добавлении/изменении товара.

---

### Практика 25 — Push-уведомления и напоминания

**Для чего:** уведомлять пользователя даже когда вкладка закрыта.

* Реализованы Web Push уведомления через `web-push`.
* Пользователь может подписаться на появление товара по названию.
* При добавлении товара сервер проверяет совпадения с напоминаниями.
* Если пользователь офлайн — отправляется Push-уведомление в браузер.
* Если онлайн — уведомление приходит через WebSocket.

---

### Практика 26 — GraphQL и Apollo

**Для чего:** гибкий API где клиент сам выбирает нужные поля, без overfetching.

* Реализован GraphQL API на Apollo Server (отдельный сервис).
* Типы схемы:
  * `Category` — категория товаров
  * `Product` — товар (связь многие-к-одному с Category)
* Операции:
  * `Query`: `products`, `product(id)`, `categories`, `category(id)`
  * `Mutation`: `createProduct`, `createCategory`
* Вложенные резолверы: `Product.category` и `Category.products`.
* На фронтенде подключён Apollo Client — хуки `useQuery` и `useMutation`.
* Новая вкладка **✨ Расширенный каталог** в приложении.
* Категории товаров стали свободными — принимается любая строка.

---

### Практика 27 — Брокеры сообщений: RabbitMQ

**Для чего:** асинхронная обработка задач без блокировки основного API.

* Запущен RabbitMQ как брокер сообщений.
* Реализован **Producer** — `POST /api/tasks` принимает задачу и кладёт в очередь.
* Реализован **Consumer** — два воркера читают задачи и обрабатывают параллельно.
* Задачи автоматически распределяются между `worker1` и `worker2`.
* **Retry Logic** с экспоненциальной задержкой — 3 попытки: 1с / 2с / 4с.
* **Dead Letter Queue** — после 3 неудачных попыток задача уходит в `tasks_dead`.

---

### Практика 28 — Контрольная работа №5 (E-commerce)

**Для чего:** итоговый проект — полноценный интернет-магазин с корзиной, заказами и оплатой.

* Корзина покупок с сохранением в `localStorage` и синхронизацией.
* Управление инвентарём — поле `stock` у каждого товара, при заказе уменьшается.
* Оформление заказа с интеграцией **Stripe** (тестовый режим).
* История заказов пользователя.
* Таблица `orders` в PostgreSQL.
* Панель администратора для просмотра всех заказов.
* Роль `customer` вместо `user`.
* Тесты Jest — покрытие helpers (`product`, `user`).

## Архитектура

```
Браузер
  │
  ▼
Nginx :443
  ├── /api/*    → backend1:3000 / backend2:3000  (REST, Round Robin)
  ├── /graphql  → graphql:4000                   (GraphQL, Apollo Server)
  └── /*        → frontend:80                    (React SPA)

Backend
  ├── PostgreSQL  — пользователи, токены, заказы
  ├── MongoDB     — товары (с инвентарём)
  ├── Redis       — кэш товаров (TTL 60с)
  ├── RabbitMQ    — очередь задач
  └── Socket.io   — реалтайм уведомления

RabbitMQ
  ├── Очередь "tasks"      — задачи для воркеров
  └── Очередь "tasks_dead" — не обработанные задачи (DLQ)
```

## Важно: генерация SSL-сертификатов

Проект использует HTTPS. Перед первым запуском необходимо создать локальные сертификаты.

```bash
mkdir -p nginx/certs

openssl req -x509 -nodes -days 365 -newkey rsa:2048 \
  -keyout nginx/certs/key.pem \
  -out nginx/certs/cert.pem \
  -subj "/CN=localhost"
```

## Основные API

### Аутентификация
* `POST /api/auth/register`
* `POST /api/auth/login`
* `POST /api/auth/refresh`
* `GET /api/auth/me`

### Товары (MongoDB + Redis)
* `GET /api/products` — с кэшированием
* `POST /api/products`
* `PUT /api/products/:id`
* `DELETE /api/products/:id`

### Заказы (PostgreSQL + Stripe)
* `POST /api/orders` — создать заказ
* `GET /api/orders/my` — история заказов пользователя
* `GET /api/orders` — все заказы (admin)

### Задачи / очередь (RabbitMQ)
* `POST /api/tasks` — поставить задачу в очередь
